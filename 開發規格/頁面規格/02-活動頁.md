# 頁面 02：活動頁

## 基本資訊

- **路由**：`#event=<id>&hostToken=<token>&tab=<vote|heatmap>`（`hostToken`、`tab` 皆為選填參數）
- **對應現有 prototype 元件**（僅供參考）：桌面版 `EventView.tsx`、手機版 `EventScreen.tsx`——兩者共用完全相同的子元件（`VoteTab`／`HeatmapTab`／`FinalizedView`／`CancelledView`／`CommentBoard`／`EventInfoCard`），差異只在版面排列

這是唯一一個「活動已存在」時會用到的頁面。它不是四個獨立路由，而是**同一個網址依照活動狀態與使用者身分，切換成四種狀態畫面之一，外加一個永遠存在的留言板**。

## 誰在看這個頁面、預設看到什麼

哪種情況出現哪種狀態，由「活動狀態」＋「使用者身分」兩個條件決定：

| 活動狀態（`status`） | 使用者身分 | 預設顯示 |
|---|---|---|
| `active` | 主揪（`hostToken` 相符） | [狀態二：彙整結果／主揪管理畫面](#狀態二彙整結果主揪管理畫面僅-status--active) |
| `active` | 已回覆過的參與者（暱稱相符） | [狀態二：彙整結果／主揪管理畫面](#狀態二彙整結果主揪管理畫面僅-status--active) |
| `active` | 尚未回覆的參與者 | [狀態一：投票畫面](#狀態一投票畫面僅-status--active) |
| `finalized` | 任何人 | [狀態三：已定案畫面](#狀態三已定案畫面status--finalized) |
| `cancelled` | 任何人 | [狀態四：已取消畫面](#狀態四已取消畫面status--cancelled) |
| 連結已超過有效期 | 任何人（含主揪） | 不屬於這個頁面——見 [03-系統狀態畫面.md「連結已失效畫面」](./03-系統狀態畫面.md#連結已失效畫面)，投票／彙整／留言全部被攔截 |

補充規則：
- 主揪身分判定看 `hostToken`；已回覆的參與者身分判定看暱稱是否相符——兩者都只在 `status = active` 時才需要判斷「預設看哪個畫面」，因為 `finalized`／`cancelled` 各自只有一種畫面，不受身分影響
- 分享連結可以帶 `tab=vote` 或 `tab=heatmap` **覆蓋上表的預設值**，但只在 `status = active` 時有意義（例如主揪分享給還沒投票的人時，直接帶對方進投票畫面）；`finalized`／`cancelled` 狀態下 `tab` 參數不影響顯示，因為那兩種狀態各自只有一種畫面可看

## 狀態一：投票畫面（僅 `status = active`）

- **對應 User Story**：[002：免登入投票，暱稱在活動內全域唯一](../功能需求.md#user-story-002免登入投票暱稱在活動內全域唯一)
- **對應 FR**：FR-3

功能：
- 輸入暱稱（必填）、聯絡 Email（選填）、密碼（選填）
- **暱稱唯一性判定**（見 [規格書.md「暱稱唯一性判定規則」](../規格書.md#42-各功能詳細規格)）：
  - 跟既有紀錄完全不衝突 → 視為新參與者
  - 跟既有參與者衝突、對方沒設 Email／密碼 → 視為同一人，直接允許覆蓋
  - 跟既有參與者衝突、對方有設 Email 或密碼 → 需提供相符的驗證資訊才能修改，否則阻擋並提示明確文案
  - 跟主揪姓名衝突 → 一律阻擋，不可透過投票流程取得或修改主揪身分（Scenario 5）
- 每個候選時段三態勾選：可行／可能可以／不行；**未特別勾選的時段一律視為「可行」**（Scenario 8，刻意的產品設計，不是缺陷）
- 依星期幾批次勾選（全部／平日／週末／週一至週日個別）
- 清單檢視／行事曆檢視切換，兩種檢視操作同一份資料，切換不遺失已勾選狀態
- 投票已截止時：畫面轉為唯讀，提示「請聯繫主揪重新開放投票」（Scenario 9）
- 活動已取消或已定案時，這個畫面不會出現——投票畫面**只在** `status = active` 時存在

## 狀態二：彙整結果／主揪管理畫面（僅 `status = active`）

- **對應 User Story**：[003：查看彙整結果](../功能需求.md#user-story-003查看彙整結果)、[004：一鍵定案](../功能需求.md#user-story-004一鍵定案)
- **對應 FR**：FR-4（彙整統計）、FR-5（主揪定案）、FR-7（狀態管理，主揪操作入口）

### 所有使用者都看得到

- 顯示所有至少 1 人標示「可行」或「可能可以」的候選時段，依分數排序（**非僅交集**，Scenario 1）
- 預設顯示前 3 名，可展開查看全部（最多 20 個，等於候選時段上限，Scenario 2）
- 完全沒有共同支持的時段時，顯示明確空狀態文案（例如「目前還沒有大家都能配合的時段」），不能是空白畫面（Scenario 3）
- 尚無任何回覆時，顯示「尚無人回覆」（Scenario 4）
- 彙整結果透過定期輪詢更新，不需要使用者手動重新整理（Scenario 5；確切輪詢間隔待工程 kickoff 定案，見 [規格書.md 第 6 節](../規格書.md#6-開放問題工程團隊-kickoff-時需一起決定)）
- 清單檢視／行事曆檢視切換（Scenario 6）
- 已回覆名冊：暱稱、對每個時段的回覆狀態摘要

### 只有主揪看得到（需先通過身分驗證：姓名＋Email 完全比對，區分大小寫，見 [規格書.md 5.4 節](../規格書.md#54-api-端點設計)）

- 選定一個候選時段作為定案候選、填寫定案備註
- 「確認最終時間並定案」：所選時段必須存在於候選清單中（Scenario 3），需經二次確認
- 「編輯活動資訊」入口 → 開啟 [編輯活動資訊 Modal](./04-彈出視窗與全域元件.md#編輯活動資訊-modal)
- 「取消活動」入口 → 開啟 [取消活動 Modal](./04-彈出視窗與全域元件.md#取消活動-modal)
- 若投票已截止：顯示「重新開放投票」入口 → 開啟 [重新開放投票 Modal](./04-彈出視窗與全域元件.md#重新開放投票-modal)

## 狀態三：已定案畫面（`status = finalized`）

- **對應 User Story**：[004：一鍵定案](../功能需求.md#user-story-004一鍵定案) Scenario 5、[005：定案通知（Email）](../功能需求.md#user-story-005定案通知email)
- **對應 FR**：FR-6（定案通知／出席名單定義）

功能：
- 顯示最終時段（日期／時段，`date_only` 模式不顯示時段）、定案備註
- 提供「加到日曆」（匯出）與下載 `.ics` 的操作
- 出席名單：**只列出對最終時段勾選「可行」的參與者**，勾選「可能可以」者不列入名單，但仍會收到定案通知（Scenario 5）
- 提供一鍵複製「聚會敲定通知」文字的操作，方便主揪轉貼到既有的 LINE 群組
- 主揪限定：「重新開放投票」「取消活動」入口，對應同一組 Modal（見下方彈出視窗文件）
- 若最終時段日期已過（活動已結束），畫面樣式需與「即將舉行」有所區別，但功能不變

## 狀態四：已取消畫面（`status = cancelled`）

- **對應 User Story**：[006：活動狀態管理（取消／重新開放）](../功能需求.md#user-story-006活動狀態管理取消重新開放) Scenario 1、3
- **對應 FR**：FR-7

功能：
- 顯示「活動已取消」與取消時間
- 純顯示，沒有投票、彙整、定案等互動——全部關閉
- **留言板仍然開放**（見下方）——這是刻意設計：「已取消」只擋新投票，不擋留言（Scenario 3），跟「連結已失效」（見 [03-系統狀態畫面.md](./03-系統狀態畫面.md)）會擋掉所有互動不同，是兩條獨立的判斷邏輯

---

## 留言板（狀態一～四共用，永遠顯示在頁面最下方）

- **對應 User Story**：[008：留言互動](../功能需求.md#user-story-008留言互動)
- **對應 FR**：FR-9

功能：
- 暱稱（必填，≤20 字，可與投票畫面的暱稱輸入共用同一個狀態）＋留言內容（必填，純文字，≤200 字）
- 送出前需持續顯示「在這邊留言會被寄信喔」這類提示（不需先點擊或聚焦欄位才出現，Scenario 2）
- 每頁最多 10 筆，分頁載入，不一次把所有留言載入（Scenario 6）
- 同一來源（IP 或瀏覽器/session）短時間內留言次數有上限，超過時阻擋並提示稍後再試（Scenario 7，確切門檻待定，見 [規格書.md 第 6 節](../規格書.md#6-開放問題工程團隊-kickoff-時需一起決定)）
- 主揪可刪除任一則留言（軟刪除，資料庫仍保留紀錄），但**不能編輯**任何留言（含自己的），一般參與者無法刪除或編輯任何留言（Scenario 8、9）
- 留言板關閉的**唯一**條件是「連結已失效」（見 [03-系統狀態畫面.md](./03-系統狀態畫面.md#連結已失效畫面)），跟活動是否被取消無關——這跟投票的守門邏輯（取消即擋）是兩條完全獨立的規則，不可混用
