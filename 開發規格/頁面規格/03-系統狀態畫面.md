# 頁面 03：系統狀態畫面

這兩個不是使用者會主動導覽過去的畫面，而是[活動頁](./02-活動頁.md)在特定條件下必須攔截、改顯示的例外狀態。[規格書.md](../規格書.md) 反覆強調「不能顯示空白或看起來像錯誤」，這兩個畫面就是把這個原則具體落地。

---

## 連結已失效畫面

- **對應 User Story**：[006：活動狀態管理（取消／重新開放）](../功能需求.md#user-story-006活動狀態管理取消重新開放) Scenario 5、6
- **對應 FR**：FR-10

### 觸發條件（兩條獨立路徑，見 [規格書.md 4.2 節 FR-10](../規格書.md#42-各功能詳細規格)）

| 情境 | 失效判斷基準 | 失效時機 |
|---|---|---|
| 已定案（`status = finalized`） | 最終時段日期 | 距今超過 7 天 |
| 已取消（`status = cancelled`） | 取消時間 | 距今超過 7 天 |
| 進行中（`status = active`） | 不適用 | 不論建立多久都不會因此失效 |

### 功能要求

- 任何人（含主揪）開啟連結都要看到明確的「連結已失效」文案，不是通用錯誤畫面、不是空白頁
- 投票、留言、查看彙整**全部**被阻擋——這跟「已取消但未滿 7 天」不同，後者仍可留言（見 [02-活動頁.md 狀態四](./02-活動頁.md#狀態四已取消畫面status--cancelled)）

### ⚠️ 現況落差（需要特別留意）

目前的 prototype **沒有**做出這個畫面。`isLinkExpired()` 判斷邏輯已經寫在 `src/lib/eventStatus.ts`，讀取資料的函式在偵測到失效連結時只會丟出一個一般錯誤（訊息是「此活動連結已失效（活動結束超過 7 天）」），被前端接住後顯示的是下方的「讀取錯誤畫面」，不是專屬的失效畫面。**這是 Phase 1 需要新增的畫面，不能直接照抄現有實作。**

---

## 讀取錯誤畫面

- **觸發條件**：活動 ID 不存在、網路錯誤、其他讀取失敗（不含「連結已失效」——那個要走上面的專屬畫面，不能混在一起）
- **對應 FR**：無特定 User Story／FR 對應，屬於系統防呆需求，但缺了這個畫面，任何非預期的讀取失敗都會讓使用者卡在死路上

### 功能要求

- 顯示「讀取失敗」與具體錯誤訊息
- 提供「返回建立新活動」之類的明確出路
