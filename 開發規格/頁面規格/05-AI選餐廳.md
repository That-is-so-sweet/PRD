# 頁面 05：AI 選餐廳

## 基本資訊

- **觸發時機**：活動狀態為「已定案」（`status = finalized`）時，[已定案畫面](./02-活動頁.md#狀態三已定案畫面status--finalized)上**登入中的主揪**限定的入口（見下方「0. 存取權限」，依賴 FR-12 的登入狀態）
- **對應 User Story**：[009：AI 選餐廳](../功能需求.md#user-story-009ai-選餐廳phase-1-範圍)
- **對應 FR**：FR-11
- **形式**：疊加在已定案畫面之上的浮層（不改變網址），不是獨立路由，性質上跟 [04-彈出視窗與全域元件.md](./04-彈出視窗與全域元件.md) 的其他 Modal 一致，因規則較多獨立成篇
- **對應現有 prototype 元件**（僅供參考，畫面可重新設計）：`src/mobile/AIRecommend/AIRecommendFlow.tsx` 及其子元件，共 2 步驟（偏好表單 → 候選結果）；不需要「重述需求確認」或「參與者共識投票」這類額外步驟，主揪直接從結果中選定一間即完成

## 這個功能要做什麼

已定案的活動只解決了「什麼時候」，主揪接下來還要自己決定「去哪吃」。這個功能讓主揪填幾個選填偏好後，直接由 AI 列出幾間餐廳，選一間就完成，並產出一則可以直接轉貼給參與者的完整訊息。

### 0. 存取權限

- **「產生推薦」入口只對登入中的主揪開放**（對應 [User Story 010](../功能需求.md#user-story-010主揪登入與主揪首頁phase-1-追加範圍) 定義的登入態）：一般參與者、或目前處於登出狀態的主揪，**完全看不到**「試試看」按鈕，也看不到還沒有推薦結果時的整個提示區塊——不是顯示成灰階或禁用狀態，而是連同整個區塊都不渲染（[功能需求.md Scenario 9](../功能需求.md#user-story-009ai-選餐廳phase-1-範圍)）。**曾評估過改成「按鈕禁用＋提示『請先登入，並且你是主揪才可以使用這個功能』」，後續討論維持完全隱藏**：理由是同一個已定案畫面上其他主揪限定操作（重新開放投票、取消活動）本來就是整個消失、不是顯示灰階，維持隱藏才能讓畫面內的權限視覺語言一致
- **例外**：一旦主揪已經選定某間餐廳，這個結果本身（店名／評分／價位／地址，唯讀）改成對所有人（含未登入者）可見，但「試試看」／「重新選擇」按鈕仍然只有登入中的主揪看得到、按得到（[功能需求.md Scenario 10](../功能需求.md#user-story-009ai-選餐廳phase-1-範圍)）
- 這條權限規則的判斷依據就是 FR-12「主揪登入」——主揪身分驗證（含這裡的存取權限判斷）以登入 session 為唯一依據

### 1. 輸入畫面

| 欄位 | 必填／選填 | 規則 |
|---|---|---|
| 地點 | 選填 | **單一自由輸入文字框**，提示文字引導範例：「捷運站名稱（例如：中山站）」「特定地區（例如：北車附近）」。**不提供**依 GPS 定位的距離篩選選項——理由：需要瀏覽器 GPS 權限，且主揪常是提前預約、人不一定在活動地點附近，實用性不高 |
| 其他偏好（與會關係、預算、人數、硬體情境、飲食偏好等） | 選填 | 沿用既有標籤式設計即可；**飲食偏好需能表達忌口／過敏**（例如「不吃牛肉」「對花生過敏」），不是只有素食／辣度兩個選項；**畫面上每個輸入選項都要清楚標示「選填」**，避免使用者誤以為必須填完才能繼續（Scenario 1） |

不論是否填寫任何欄位，主揪都可以直接點擊「產生推薦」（Scenario 1）。

### 2. 結果畫面

- **顯示 3 到 5 間餐廳**（不是固定 5 間，細節見下方「AI 資料來源與串接方案」）：優先回傳 5 間；只有指定地點範圍內符合條件的餐廳不足 3 間時，才可以放寬範圍搜尋，且放寬後回傳結果的地址必須與放寬後的範圍相符，不可以「聲稱已放寬、結果卻還在原範圍」
- 每一間都要顯示以下欄位，比照 Google Maps 單一店家頁會有的資訊（Scenario 3）：
  - 店名、Google 評分、評論數
  - 目前營業時間
  - 價位等級（$／$$／$$$／$$$$）與每人平均消費金額區間（新台幣）
  - 地址、電話、料理類型
  - 距離資訊（最近捷運站或地標＋預估步行分鐘數；無法確認時留空，不可自行估算）
  - 推薦理由（需具體指出符合條件的菜色／特色，同批結果不可用重複句型）
  - Google Maps 連結（可直接開啟）
  - **任何一個欄位查無資訊一律留空，不可用推測值頂替**，也不可以編造餐廳本身不存在的資訊
- **Google Maps 連結不是 AI 直接生成的**——後端是用店名去比對 AI 服務回應中另外隨附的真實搜尋來源取得網址（技術細節見下方「AI 資料來源與串接方案」）；如果比對不到對應網址，這一筆結果**不顯示地圖連結**（例如只顯示地址與電話，不顯示「查看地圖」按鈕），**不可以由前端或後端自行拼湊一個網址頂替**
- **主揪直接點選一間即完成選定**（Scenario 4）：
  - **不需要**額外的「重述需求」確認步驟——AI 直接依填寫內容（或無填寫時的預設邏輯）產生結果，不用先跟主揪確認過查詢內容才繼續
  - **不需要**參與者共識投票流程——原規劃讓參與者對候選餐廳表態「我可以／不行」的機制已移除，主揪選了就算數
- **選定後的視覺回饋**：選定的那間維持正常呈現，其餘未選中的餐廳在畫面上轉為**灰階／降低透明度**，直觀呈現「已經是這間了」（Scenario 4）
- **不提供**「加入我的最愛」收藏功能，也**不提供**任何歷史搜尋紀錄清單（Scenario 5）——如果本次結果都不滿意，主揪可以直接點「重新整理」再產生一次，但這個動作會計入下方的使用次數（Scenario 6）

### 3. 選定後的一鍵複製

- 選定一間餐廳後，畫面提供「一鍵複製」，複製內容需**同時包含前後兩段**（Scenario 7）：
  1. **前半段**：已定案的聚會資訊——活動名稱、主揪、日期、時間、備註（沿用 [已定案畫面「一鍵複製聚會敲定通知」](./02-活動頁.md#狀態三已定案畫面status--finalized)已有的文案邏輯）
  2. **後半段**：剛選定的餐廳資訊——店名、評分、地址、Google Maps 連結（若這筆結果沒有比對到連結，這一行省略，不可以放空白網址或編造一個）
- 這是給主揪直接轉貼到既有 LINE 群組用的完整訊息，**不是**只複製餐廳資訊的舊版行為
- 裝置支援 Web Share API 時，複製鈕旁並排提供「分享」按鈕，同一則訊息可直接叫出原生分享選單；不支援時不顯示（規則同 [已定案畫面](./02-活動頁.md#狀態三已定案畫面status--finalized)與 [分享 Modal](./04-彈出視窗與全域元件.md#分享-modal)）

### 4. 使用次數限制

- 為控制第三方地圖／AI API 費用，使用次數**與主揪帳號綁定**（即 FR-12 的登入帳號），每位主揪每個自然月最多 **20** 次（Scenario 8）
- 「產生推薦」與「重新整理」都計入 1 次
- 達到上限時阻擋操作並提示已達本月使用上限
- 這條規則需要的登入／帳號識別機制就是 FR-12 的 Google SSO 登入態；本頁「免登入」的定位僅適用於一般參與者，主揪端登入見 [規格書.md 2.4 節](../規格書.md#24-wont-have明確排除)

## AI 資料來源與串接方案

> 以下是規劃階段研究 Perplexity API 後整理出的建議做法，供工程團隊參考；實際串接細節（Prompt 用字、schema 設計等）開發時仍可依測試結果調整。

採用 Perplexity 的 Agent API（`Create Agent Response` 端點），不使用 Router API（`Create Chat Completion` / `Create Response`），也不採用 Google Places API 路線：

- **為什麼選 Agent API**：(1) Perplexity 已公告舊版 Sonar／Chat Completions API 將於 2026-09-27 停止支援；(2) Agent API 官方文件明確示範「網路搜尋＋json schema 結構化輸出」搭配使用，符合「依條件即時搜尋→輸出固定格式」的需求；Router API 則需要自行額外串接搜尋工具
- **強制結構化輸出**：呼叫時必須在請求中設定 `response_format` 為 `json_schema`（strict mode）強制輸出格式，**不能只在 prompt 文字裡拜託模型輸出純 JSON**——直接在 perplexity.ai 網站對話框測試時偶爾會夾雜額外文字，這是正常現象，因為網站介面沒有這個強制參數
- **筆數與放寬邏輯（見上方「2. 結果畫面」）**：優先回傳 5 間；指定地點範圍內符合條件的餐廳不足 3 間時才放寬範圍，回傳結果的地址必須與放寬後的範圍相符
- **完整資料欄位**：評論數、目前營業時間、每人平均消費金額區間、電話、料理類型、距離資訊等，皆須在 System Prompt 中定義為結構化輸出的必要欄位（見上方「2. 結果畫面」欄位清單）；查無資訊一律留空，不可用推測值頂替
- **Google Maps 連結的防編造機制**：**不可要求 AI 模型自行生成網址**——模型把網址當結構化輸出的一部分時，容易產生格式錯誤或編造的連結。正確做法：後端用每筆結果的店名，比對 Perplexity Agent API 回應中另外隨附的真實引用來源（`citations`／`search_results` 欄位）取得網址；比對不到對應網址時，該筆結果的地圖連結欄位留空，前端顯示對應的容錯呈現（例如只顯示地址與電話、不顯示「查看地圖」按鈕），不可以由前端或後端自行拼湊一個網址頂替
- **仍待工程 kickoff 確認**：(a) Agent API 本身的呼叫計費方式與費用；(b) `citations`／`search_results` 欄位在實際回應中的確切資料結構、是否穩定包含每間餐廳的來源，需要工程團隊第一輪測試時實際記錄確認

**規劃階段實測發現的問題**（初版 Prompt 丟入 Perplexity 測試取得 4 筆結果、人工核對後的發現，上方 System Prompt 設計已針對這些問題修正）：

| 觀察到的問題 | 對應修正 |
|---|---|
| Google Maps 連結用經緯度座標查詢，連結不穩定，有時無法直接跳到正確店家頁面 | 完全移出 JSON schema，改由後端比對 `citations`／`search_results` 取得真實網址 |
| `notes` 欄位聲稱「已放寬地理範圍」，但實際結果地址仍在原範圍內，說明與實際結果不一致 | System Prompt 明確要求 notes 只能寫「實際發生的事」，且需與回傳結果地址一致 |
| 推薦理由有多筆用了幾乎相同的句型，個別化程度不足 | System Prompt 要求具體指出菜單特色，且同批結果不可重複句型 |
| 距離／交通時間資訊混在推薦理由的文字敘述裡，不利前端拆解顯示 | 拆成獨立的 `distance_info` 結構化欄位，且不確定時明確要求填 null，不可自行估算 |
| 價位僅有 `$` 符號等級，缺乏具體金額數字，無法用於精準預算比對 | 新增每人平均消費金額的結構化欄位（區間數字） |

其他值得留意的實測細節：`citations`／`search_results` 欄位在不同次呼叫之間的資料結構略有出入，後端比對邏輯需要容錯處理；店名含分店資訊（如「○○（信義店）」）時比對成功率較低，建議先做字串正規化再比對；初版測試回應時間落在 8–15 秒，前端需要明確的載入中狀態設計。完整的測試方法、System／User Prompt 全文與更多實測記錄，見附錄 [AI選餐廳_Perplexity串接執行計畫書.md](../附錄/AI選餐廳_Perplexity串接執行計畫書.md)。

## 不屬於這個頁面的事

- 活動尚未定案（`status = active` 或 `cancelled`）時，這個功能不會出現——只有已定案活動才需要「去哪吃」這個決策
- 上方「AI 資料來源與串接方案」屬於後端技術實作細節，不影響本文件描述的畫面行為
