## 1. Background 背景

### 1.1 產品定位

**揪甘心** — 聚會時間協調工具。核心主張：參與者免登入、免加好友，透過一個連結就能勾選可行時段；主揪（發起人）可以一鍵彙整所有人的時間、看熱點圖、拍板定案。

### 1.2 核心問題與商業假設

**痛點（Who & Why）**
主揪在揪團前期需要反覆詢問、手動整理每個人的可行時間，平均花 5 天、來回問好幾輪才能定案；參與者則因為要開行事曆確認、打字回覆而拖延，甚至因行程未定而錯失參與機會。

**核心商業假設（Value）**
如果我們用「時間投票連結」取代「LINE 群組人工喬時間」，主揪能將喬時間的決策時間從平均 5 天縮短，參與者也會願意用勾選取代打字回覆，不需要加好友、不需要開行事曆手動比對。

**驗證方式**：已用一版純前端 prototype 驗證過核心互動流程並收集初步 UX 回饋，現在進入正式開發階段：具備完整後端、資料庫的產品。

### 1.3 產品原則

> 先讓活動能成團，再優化活動體驗。第一階段聚焦驗證「喬時間」這個核心假設，並且**在免登入、免加好友的低門檻前提下**完成。

## 2. Scope Boundary 範圍邊界

### 2.1 系統範圍

| 系統組成 | 正式產品範圍 |
|---|---|
| 前端 Web App | 依本文件第 4 節功能需求開發，介面設計可另外全新設計，不需沿用任何既有畫面結構 |
| 後端 API 服務 | **需要**（見第 5 節） |
| 資料庫 | **需要**（關聯式資料庫，見第 5.3 節） |
| 使用者身分／權限驗證 | 需要伺服器端簽發、驗證的安全機制（見第 5.4／5.6 節） |
| 通知／寄信 | **需要**（Email，見第 5.5 節） |
| 跨裝置同步 | **需要**（資料存伺服器端後自然具備） |
| 排程任務 | **需要**（台灣假日資料同步，見第 5.7 節） |

### 2.2 Phase 1（Must-have）範圍

1. 主揪發起活動，系統自動產生可分享連結（表單支援逐步草稿保存，避免中途離開遺失內容）
2. 參與者透過連結免加好友、免登入即可勾選可行時段
3. 系統自動彙整所有人勾選結果，顯示所有「有人可以配合」的時段
4. 主揪可查看彙整結果並一鍵確認最終時間
5. 確認後系統自動以 Email 通知所有參與者
6. 主揪可取消活動或重新開放投票，這兩個動作都會通知已回覆的參與者
7. 參與者與主揪可在活動頁面留言（純文字，有防灌水與分頁機制，主揪可刪除留言）

### 2.3 Should-have（Phase 1 候選加值項）

- 未回覆者的提醒通知
- 時段衝突時的次佳選項建議
- 留言可編輯／參與者自行刪除自己的留言

### 2.4 Won't-have（明確排除）

**Phase 2｜減輕主揪壓力**：快閃聊天室、分帳功能
**Phase 3｜提升聚會體驗**：飲食護照、菜單翻譯、邀請函
**明確排除，且與「免登入」定位衝突，需要獨立評估**：任何形式的帳號系統／OAuth 登入（例如串接 Google 帳號讓使用者跨裝置查看「我的聚會」）——這會讓產品同時存在「免登入」與「需登入」兩套邏輯，Phase 1 不做，是否要做需要先確認會不會弱化核心賣點，見第 6 節開放問題
**未列入任何階段但被明確排除**：跨平台行事曆自動雙向同步（單向「加入日曆」匯出已完成，不受此排除影響）

## 3. User Story / Use Case

### 3.1 角色定義

- **主揪（Host）**：發起活動的人，擁有查看彙整結果、定案、取消、重開活動、編輯活動基本資訊、刪除留言的權限
- **參與者（Participant）**：透過分享連結進入活動、勾選可行時段、留言的人（免登入）

### 3.2 關鍵 Use Case

**UC-1：主揪建立活動**
- 前置條件：無（免登入）
- 主流程：主揪填寫活動名稱、主揪姓名、候選時段模式（純日期或指定時間，兩者擇一，建立後不可變更）、候選時段（1～20 個）、回覆截止時間（必須晚於目前時間）、（選填）主揪 Email、地點與說明 → 系統建立活動並產生可分享連結；若填寫了主揪 Email，系統寄送一封含分享連結的通知信
- 表單填寫過程中，每完成一個步驟就把目前內容存到瀏覽器本機（例如 `localStorage`）；使用者中途離開、重新整理、或不小心跳出，回來時可以接續填寫。開始一個全新的建立流程時，會覆蓋掉前一次未完成的草稿（同一時間只保留一份草稿）
- 例外：候選時段為空或超過 20 個、活動名稱／主揪姓名為空或超過長度限制、主揪 Email 格式不正確、回覆截止時間為空或不晚於目前時間 → 前端阻擋送出並提示；即使前端已擋，後端仍需重新驗證同一組規則，任何一項不通過就整筆拒絕並回傳明確的錯誤訊息（不可只讓前端擋、後端照單全收）

**UC-2：參與者投票**
- 前置條件：持有有效的活動分享連結，且活動狀態為進行中、投票未截止
- 主流程：輸入暱稱（＋ Email、密碼，皆選填）→ 針對每個候選時段選擇可行／可能可以／不可行（未特別選擇的時段視為「可行」，見 FR-4 說明）→ 送出後可回連結修改
- 暱稱唯一性檢查：見 FR-3
- 例外：活動已取消或已定案 → 不接受新投票；投票已截止 → 提示聯繫主揪重新開放；暱稱衝突且身分核對不過 → 阻擋並提示

**UC-3：主揪查看彙整並定案**
- 前置條件：輸入的主揪姓名（若活動有登記 Email，需同時輸入 Email）與活動建立時登記的資料完全相符（區分大小寫，不做寬鬆比對），經伺服器端驗證通過
- 主流程：查看彙整結果（顯示所有至少 1 人標示可行或可能可以的時段）→ 選定最終時段（＋備註）→ 確認定案 → 系統通知所有已回覆的參與者
- 例外：選擇的時段不存在於候選清單 → 阻擋；姓名／Email 與登記資料不相符 → 拒絕操作

**UC-4：主揪取消／重新開放活動**
- 主流程：主揪可將已定案活動改回進行中重新收集回覆（不清除既有回覆內容，只清除先前選定的最終時段、並要求新的截止時間），或直接取消整個活動（同樣需通過 UC-3 的身分驗證）；取消與重新開放都會通知已回覆的參與者

**UC-5：留言互動**
- 前置條件：活動連結尚未失效（見 FR-11）
- 主流程：參與者／主揪輸入暱稱與留言內容（純文字，≤200 字）→ 送出前提示「留言會觸發通知信」→ 留言出現在列表中（每頁 10 筆，分頁載入）
- 主揪可刪除任何一則留言（不可編輯他人留言內容）
- 例外：活動連結已失效 → 阻擋留言；同一來源短時間內留言次數超過限制 → 阻擋並提示稍後再試（見 4.4 節防濫用）

## 4. Feature Requirement 功能需求（Phase 1 詳細規格）

### 4.1 功能需求總表

| 編號 | 功能 | 說明 | 驗收標準 |
|---|---|---|---|
| FR-1 | 建立活動 | 主揪輸入標題、主揪姓名、候選時段模式、候選時段（≤20）、回覆截止時間、主揪 Email（選填）、地點／說明（選填），過程支援草稿保存 | 送出後產生全域唯一活動 ID 與可分享連結；後端對所有欄位重新驗證，任一規則不符即整筆拒絕 |
| FR-2 | 分享連結 | 產生的連結需可被任何人（無帳號）開啟並看到活動內容 | 連結不含可被輕易猜測或暴力枚舉的活動 ID；分享連結本身不含任何可用於取得主揪管理權限的資訊 |
| FR-3 | 免登入投票與暱稱唯一性 | 參與者輸入暱稱＋ Email＋可選密碼，針對每個候選時段選擇可行／可能可以／不可行 | 同一活動內，主揪姓名與所有參與者暱稱共用同一個唯一性檢查（不分大小寫）；衝突時的判定規則見 4.2 節 |
| FR-4 | 彙整統計與投票畫面 | 系統計算每個候選時段的可行／可能可以／不可行人數與名單；顯示所有至少 1 人標示可行或可能可以的時段（非僅交集）；支援清單／行事曆兩種檢視、依星期幾批次勾選 | 預設顯示前 3 名，可展開至全部（最多 20 個）；未特別勾選的時段一律視為「可行」（設計決策，非缺陷，見 4.2 節說明）；彙整結果透過輪詢定期更新（間隔待技術選型後定案，見第 6 節） |
| FR-5 | 主揪定案 | 主揪從候選時段中選定最終時段，可附加備註 | 僅通過主揪身分驗證才能執行；定案後活動狀態變更為「已定案」；選擇的時段須存在於候選清單中 |
| FR-6 | 定案通知 | 定案後，系統對所有已留下 Email 的參與者發送通知 | 通知需包含最終時間、地點、備註；發送失敗需記錄（不可靜默丟失）；出席名單僅計入對最終時段勾選「可行」者 |
| FR-7 | 活動狀態管理 | 支援「進行中」「已定案」「已取消」狀態，及「重新開放投票」 | 已取消／已定案不可再投票；重新開放只清除最終時段設定與截止時間，**不清除任何參與者已送出的回覆**；重新開放與取消都要通知所有已回覆的參與者 |
| FR-8 | 編輯活動基本資訊 | 主揪可編輯標題／說明／地點／主揪資訊／截止時間（候選時段不可編輯） | **僅限活動狀態為「進行中」時可編輯**；已取消或已定案時，後端須拒絕編輯請求（不可只靠前端不顯示編輯入口） |
| FR-9 | 留言 | 參與者／主揪可在活動頁面留言，純文字、無法附圖或標記特定人 | 送出前提示「留言會觸發通知信」；每頁 10 筆分頁載入；有防濫用的頻率限制；主揪可刪除任何留言 |
| FR-10 | 連結有效期 | 連結在特定條件下應失效並回傳明確的「已失效」畫面，而非一般錯誤 | 兩種失效條件（見 4.2 節）：已定案活動於最終時段日期起算超過 7 天；已取消活動於取消時間起算超過 7 天。進行中的活動不論多舊都不會因此失效；失效後的活動 ID **永久不重複使用**（見 4.2 節「軟刪除」說明） |
| FR-11 | AI 選餐廳 | 活動定案後，主揪可選填地點輸入等偏好，由 AI 一次推薦 3–5 間餐廳供主揪直接選定其中一間 | 詳細規格見 4.2 節與 [頁面規格 05-AI選餐廳.md](./頁面規格/05-AI選餐廳.md)；2026-09-02 會議追加為 Phase 1 範圍，資料來源技術方案見 4.2 節「FR-11 資料來源技術方案」 |
| FR-12 | 主揪登入與主揪首頁 | 主揪需先登入（Google SSO）才能建立活動或查看「我揪的團」；參與者透過活動連結進入時完全不受影響、不需要登入 | 詳細規格見 4.2 節「FR-12」與 [頁面規格 01-建立活動頁.md](./頁面規格/01-建立活動頁.md#登入與主揪首頁2026-09-01-追加)；⚠️ 與本文件 2.4／8 節「明確排除 OAuth」既有立場直接衝突，見該節說明 |

### 4.2 各功能詳細規格

**FR-1 建立活動**

| 欄位 | 型別 | 必填／選填 | 長度／格式限制 | 驗證規則與錯誤訊息 |
|---|---|---|---|---|
| 活動名稱（title） | 字串 | 必填 | 去除頭尾空白後 1–30 字 | 空白時阻擋，提示「請輸入活動名稱」；超過 30 字阻擋，提示「活動名稱不可超過 30 字」 |
| 主揪姓名（host_name） | 字串 | **必填**（本次確認為必填，用於 FR-5 身分驗證，見 5.4 節） | 見下方「中英文長度規則」說明 | 空白時阻擋，提示「請輸入您的姓名」；超長阻擋，提示對應錯誤訊息；此欄位與所有參與者暱稱共用同一個唯一性空間（見 FR-3） |
| 主揪 Email（host_email） | 字串 | 選填 | 需符合 Email 格式（見下方建議 regex） | 有填但格式不符時阻擋，提示「Email 格式不正確」。一旦填寫，日後身分驗證需與姓名一併核對 |
| 候選時段模式（mode） | 列舉：`date_only` / `time_slots` | 必填（建立時二擇一） | — | 建立後不可變更；同一活動的候選時段不可混用兩種模式 |
| 候選時段（candidate_slots） | 陣列 | 1～**20** 筆 | `date_only`：每筆僅含日期；`time_slots`：每筆為單一時間點（日期＋時間） | 陣列為空時阻擋，提示「請至少新增一個候選時段」；超過 20 筆時阻擋，提示「候選時段最多 20 個」；前端在達到 20 筆時應直接鎖住「新增」按鈕，後端仍需二次驗證筆數 |
| 回覆截止時間（response_deadline） | 日期時間 | 必填 | 必須晚於送出當下的時間；一律以台灣時間（UTC+8）認定與顯示 | 空白時阻擋，提示「請設定回覆截止時間」；前端用日期選擇器鎖定不能選過去時間，**後端仍須重新驗證**：若送達時該時間已不在未來，拒絕整筆請求並回傳明確錯誤（例如「截止時間需晚於目前時間」），不可只信任前端 |
| 地點文字（location_text） | 字串 | 選填 | ≤200 字 | 超過 200 字阻擋 |
| 地點連結（location_url） | 字串（URL） | 選填 | 需為合法網址格式；短連結需經解析服務轉換為實際地點名稱，見第 6 節開放問題 | 格式不符時阻擋，提示「請輸入正確的網址」 |
| 活動說明（description） | 字串 | 選填 | ≤50 字 | 超過 50 字阻擋，提示「活動說明不可超過 50 字」 |
| 草稿保存 | — | — | — | 表單每完成一個步驟即寫入瀏覽器本機儲存；開始新的建立流程時覆蓋舊草稿（同時只保留一份）；這是前端 UX 需求，不需要後端支援，草稿內容不會同步到伺服器 |

**中英文長度規則（⚠️ 需要工程團隊確認的實作細節）**：主揪姓名「中文 20 字以內、英文 50 字以內」這個規則本身沒有指定「中英文混合輸入」該怎麼算。本文件先訂一個具體版本供開發：**加權字元計算**——CJK（中日韓）字元計 2 個單位，非 CJK（英數）字元計 1 個單位，總單位數上限 **40**（換算：純中文最多 20 字、純英文最多 40 字）。這個版本能一致處理中英混合輸入，但純英文上限是 40 字而非原本講的 50 字。如果產品需要「純英文情境一定要到 50 字」，需要改成「先判斷輸入主要語言、套用對應獨立上限」這種更複雜的規則——**這點請工程 kickoff 時跟產品端再次確認要採用哪一版**，本文件先以加權字元版本為預設實作依據。

**Email 格式驗證**：建議直接採用與瀏覽器 `<input type="email">` 一致的 HTML5 標準 regex，避免前後端判斷結果不一致：
```
^[a-zA-Z0-9.!#$%&'*+/=?^_`{|}~-]+@[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?(?:\.[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)+$
```
前後端都要用同一套規則，避免出現「前端過了、後端擋掉」或反過來的情況。

**FR-3 免登入投票與暱稱唯一性**

| 欄位 | 型別 | 必填／選填 | 長度／格式限制 | 驗證規則與錯誤訊息 |
|---|---|---|---|---|
| 暱稱（nickname） | 字串 | 必填 | 與主揪姓名相同的中英文長度規則 | 空白時阻擋；超長阻擋；唯一性規則見下方 |
| 聯絡 Email（email） | 字串 | 選填 | 同 FR-1 的 Email regex | 有填但格式不符時阻擋 |
| 密碼（password） | 字串 | 選填 | 不限制格式 | 一旦於某個暱稱下設定，之後用同一暱稱回來修改需輸入相同密碼；伺服器端儲存需雜湊，不可明碼存放 |
| 每個候選時段的可行狀態（availability） | 列舉：`available` / `if_needed` / `unavailable` | 每個候選時段各有一筆狀態 | — | **未特別勾選的時段一律視為「可行」**——這是刻意的設計決策：系統只會知道已回覆的人，無法區分「還沒回覆」跟「明確表態不行」，強制每格勾選對降低填寫門檻沒有幫助，因此不做強制逐格勾選 |

**暱稱唯一性判定規則**（同一活動內，主揪姓名＋所有參與者暱稱共用一個唯一性空間，不分大小寫比對）：

1. 新送出的暱稱若跟活動裡任何一筆既有紀錄（不論是主揪姓名，還是另一位參與者的暱稱）**完全不衝突** → 直接視為新參與者，正常送出
2. 新送出的暱稱跟**某位既有參與者**的暱稱衝突：
   - 若該既有回覆**沒有設定 Email、也沒有設定密碼** → 視為同一人，直接允許覆蓋修改既有回覆（不需要額外驗證）
   - 若該既有回覆**有 Email 或密碼** → 新送出的請求必須提供相符的 Email，或相符的密碼，兩者符合其一才允許覆蓋；都不符合則阻擋送出，並用明顯的警示文案提示「這個暱稱已經有人使用，如果是你本人，請輸入當初設定的 Email 或密碼」
3. 新送出的暱稱跟**主揪姓名**衝突 → **一律阻擋**，提示「這個暱稱已被使用」，不允許透過投票流程「變成」主揪或修改主揪資料（主揪身分只能透過 UC-3 的姓名＋Email 核對取得，不透過暱稀衝突機制取得）——**這條是本文件基於你先前確認「主揪與參與者共用唯一性空間」推導出的具體規則，如果你希望允許某種例外，麻煩明確告知**

**FR-4 彙整統計與投票畫面（補充）**

- 彙整結果顯示規則：只要一個候選時段至少有 1 人標示「可行」或「可能可以」，就列入彙整清單（不是只顯示交集/所有人都可行的時段）；預設顯示排序前 3 名，主揪／參與者可點「顯示更多」展開至完整清單（最多 20 個，等於候選時段上限）
- 如果所有已回覆的人對每個候選時段都選「不行」，彙整清單會是空的，畫面需要顯示明確的空狀態文案（例如「目前還沒有大家都能配合的時段」），不能顯示空白或看起來像錯誤
- 參與者可依「星期幾」篩選候選時段（全部／平日／週末／週一至週日個別），一次將篩選出的時段批次設為可行／可能可以／不可行
- 候選時段支援「清單檢視」與「行事曆檢視」兩種顯示模式
- 彙整結果更新機制：不做即時推播（WebSocket），採用**輪詢**方式定期重新拉取最新彙整結果；確切輪詢間隔（建議 15–30 秒）待工程 kickoff 時依技術選型與伺服器負載評估後定案

**FR-6 定案通知（補充：出席名單定義）**

定案後系統產生的出席名單，僅計入對最終時段勾選「可行」的參與者；勾選「可能可以」者不計入出席名單，但仍會收到定案通知（通知對象是所有留下 Email 的參與者，不論是否列入出席名單）。

**FR-7 活動狀態管理（補充）**

- 重新開放投票：只做兩件事——① 清除先前選定的最終時段（`final_slot_id`／`final_note`）；② 要求主揪設定新的截止時間（若原截止時間已過期，須自動順延或由主揪重新指定）。**不會**清除任何參與者已經送出的回覆內容——大家先前勾選的可行狀態原封不動保留，重新開放只是讓大家可以繼續投票／修改
- 重新開放投票後，系統需通知所有已回覆的參與者（Email，見 FR-11）
- 取消活動後，除了阻擋新投票，**不會**阻擋留言——留言的開放與否只看連結是否失效（見 FR-10），跟活動是否被取消是兩條獨立的判斷邏輯

**FR-8 編輯活動基本資訊（補充）**

編輯權限的判斷**必須放在後端業務邏輯層**，不能只靠前端不顯示編輯按鈕：活動狀態不是「進行中」（也就是已取消或已定案）時，後端收到編輯請求要直接拒絕並回傳明確錯誤，不可依賴前端沒有開放編輯入口就假設不會有這種請求送達。

**FR-9 留言（補充）**

| 欄位 | 型別 | 必填／選填 | 長度／格式限制 | 驗證規則與錯誤訊息 |
|---|---|---|---|---|
| 暱稱（nickname） | 字串 | 必填 | 與主揪姓名相同的中英文長度規則 | 空白時阻擋；超長阻擋 |
| 留言內容（message） | 字串 | 必填 | 去除頭尾空白後 1–200 字 | 空白時阻擋，提示「請輸入留言內容」；超過 200 字阻擋，提示「留言內容不可超過 200 字」 |

- 留言內容僅支援純文字，不支援附圖、不支援標記（@）特定使用者
- 留言列表分頁：每頁最多 10 筆，需要載入更多時分頁請求
- 防濫用機制：同一來源（IP 或瀏覽器/session）在短時間內的留言次數需要有上限（建議例如 1 分鐘內最多 5 則，實際門檻待技術選型後由工程團隊決定，見第 6 節）；超過限制時阻擋並提示稍後再試
- 主揪可以刪除任何一則留言（含其他參與者留的）；**不提供編輯他人留言的功能**，避免產生「主揪竄改留言內容」的信任疑慮。留言者本人是否能編輯／刪除自己的留言，列入 Should-have，Phase 1 不做

**FR-10 連結有效期（補充：兩種失效條件）**

| 情境 | 失效判斷基準 | 失效時機 |
|---|---|---|
| 已定案（`status = finalized`） | 最終時段日期 | 距今超過 7 天 |
| 已取消（`status = cancelled`） | 取消時間（`cancelled_at`） | 距今超過 7 天 |
| 進行中（`status = active`） | 不適用 | 不論建立多久都不會因此失效 |

連結失效後，開啟連結應顯示明確的「已失效」畫面，投票、留言、查看彙整等所有互動都應被阻擋——這一點跟「已取消但連結未失效」的狀態不同（後者仍可留言，見 FR-7）。

**軟刪除與 ID 不重複使用（2026-09-02 會議定案）**：已失效或已取消的活動記錄在資料庫中一律採**軟刪除**（標記失效狀態，不做實體刪除），理由：如果改用硬刪除，之後新建立的活動有機率被系統重新配發到跟某個「曾經存在過」的舊活動相同的 ID，導致使用者點擊自己收藏的舊連結卻看到別人的全新活動——軟刪除保留了 ID 的佔用紀錄，從根本避免這個衝突，未來也保留視需要再做真正清運（封存／匯出後刪除）的彈性。這與 `event_comments.deleted_at` 的既有軟刪除模式一致（見 5.3 節），只是套用範圍擴大到 `events` 整張表。

**活動 ID 格式（2026-09-02 會議定案，補充 5.6 節）**：活動 ID 為一串**約 16 字元**的亂數字串（英數混合，小寫），**不依建立時間或任何遞增序號產生**，避免被他人從既有連結推測出時間先後順序或用暴力枚舉猜出其他活動；顯示於畫面（例如分享連結）時，寬度需控制在**兩行以內**（最多不超過三行，避免顯得冗長）。

**FR-11 AI 選餐廳（2026-09-02 會議定案，Phase 1 追加範圍）**

觸發時機：活動狀態變更為「已定案」之後，主揪可在已定案畫面選擇進入這個功能（見 [頁面規格 05-AI選餐廳.md](./頁面規格/05-AI選餐廳.md) 的完整 UI 規格）。

| 子項目 | 規則 |
|---|---|
| 輸入頁面 | 僅一個**自由輸入的地點欄位**（選填），提示文字引導輸入捷運站名稱或概略地區（例如「中山站」「北車附近」）；**不提供**依 GPS 定位的距離篩選選項（800m／捷運沿線等），因為主揪常是在活動前先於他處預約，且要求瀏覽器 GPS 權限對此情境幫助有限。飲食偏好輸入需能表達**忌口／過敏**（例如「不吃牛肉」「對花生過敏」），不是只有素食／辣度兩個選項。所有輸入選項（含地點欄位、其他偏好標籤）都要在畫面上明確標示「選填」 |
| 結果頁面：筆數 | **3 到 5 間**（2026-09-02 v2 修正：不是固定 5 間）——優先回傳 5 間；只有指定地理範圍內符合條件的餐廳不足 3 間時，才可以放寬地理範圍搜尋，且放寬後**回傳結果的地址必須與放寬後的範圍相符**，不可以「聲稱已放寬、結果卻還在原範圍」 |
| 結果頁面：欄位 | 每間需顯示：店名、Google 評分、評論數、目前營業時間、價位等級（$／$$／$$$／$$$$）、每人平均消費金額區間（新台幣，如 400–800 元）、地址、電話、料理類型、距離資訊（最近捷運站或地標＋預估步行分鐘數）、推薦理由（需具體指出符合條件的菜色／特色，同批結果不可用重複句型）、Google Maps 連結。**任何一個欄位查無資訊一律留空，不可用常識或推測值頂替**，也不可以編造餐廳本身不存在的資訊 |
| Google Maps 連結來源 | **不可要求 AI 模型自行生成網址**——模型把網址當結構化輸出的一部分時，容易產生格式錯誤或編造的連結（實測已驗證：早期版本用經緯度組出的連結不穩定，見 [執行計畫書](../../docs/auth-&-AI-feature-2026-0901/AI選餐廳_Perplexity串接執行計畫書.md) 第四、八節）。正確做法：後端用每筆結果的店名，比對 AI API 回應中另外隨附的真實引用來源（例如 Perplexity Agent API 的 `citations`／`search_results` 欄位）取得網址；比對不到對應網址時，該筆結果的地圖連結欄位留空，前端需設計對應的容錯呈現（例如只顯示地址與電話、不顯示「查看地圖」按鈕），**不可以由前端或後端自行拼湊一個網址頂替** |
| 存取權限（2026-09-05 定案，同日重新確認） | **整個「產生推薦」入口對非主揪（一般參與者，或尚未登入的主揪）完全隱藏**——不是顯示成灰階或禁用按鈕，而是連同整個提示區塊一起不渲染，因為參與者本來就不該有「叫 AI 產生新推薦」這個動作。**曾經評估過的替代方案（已否決）**：把按鈕改成禁用狀態＋提示文字「請先登入，並且你是主揪才可以使用這個功能」——否決理由是這樣會跟同一個已定案畫面上其他主揪限定操作（FR-7 的「重新開放投票」「取消活動」入口）的既有做法不一致，那些入口對非主揪也是整個消失、不是顯示灰階，為了畫面內部一致性選擇維持「完全隱藏」。**例外**：一旦主揪已經選定某間餐廳，這個結果本身（店名／評分／價格／地址）改成以唯讀方式顯示給所有人（含未登入者），但「試試看」／「重新選擇」按鈕仍然只有登入中的主揪看得到、按得到。判斷依據見 FR-12：只有 FR-12 定義的「登入中的主揪」狀態為真時，才算通過這裡的權限檢查 |
| 選定行為 | 主揪從結果中直接點選一間即完成選定；**不設**參與者共識投票流程，也不需要主揪額外確認 AI 產生的查詢內容（原先規劃的「重述需求」確認步驟已移除，改為直接依填寫內容產生查詢） |
| 選定後的畫面效果 | 主揪選定後，其餘未選中的餐廳需以灰階／降低透明度呈現，直觀標示「已經定案是這間」 |
| 歷史紀錄／收藏 | **明確不做**：不提供「我的最愛」收藏功能，也不保留過去多次搜尋的歷史紀錄——避免介面複雜化，讓使用者又落入像 Google Maps 一樣要逐家比對的困擾；如果對這次結果不滿意，主揪可直接重新整理再產生一次（會計入下方使用次數扣抵） |
| 複製與通知 | 「一鍵複製」需整合**前半段**已定案的聚會資訊（活動名稱、主揪、日期、時間、備註）與**後半段**剛選定的餐廳資訊（店名、評分、地址、Google Maps 連結——若該筆沒有比對到連結則省略這一行）成一則完整訊息，供主揪一次複製轉發給參與者，不是只複製餐廳資訊 |
| 使用次數限制 | 為控制第三方地圖／AI API 費用，**與主揪帳號（例如 Gmail）綁定**，每位主揪每個自然月最多可使用 **20** 次（每次「產生推薦」或「重新整理」都計入 1 次）；超過上限時的畫面行為與扣抵是否按活動或按帳號累計，待工程 kickoff 時定案 |

> ⚠️ **與現有立場的衝突（尚未解決）**：「使用次數限制與主揪帳號綁定」隱含需要某種形式的登入或帳號識別機制，這與本文件 2.4 節、8 節「明確排除 OAuth／帳號系統」的既有立場、以及核心賣點「免登入」直接衝突。目前僅有的替代方案構想（見專案內另一份純前端 prototype 的示範性質假登入畫面）尚未經過正式評估是否符合此處對安全性與跨裝置一致性的要求。**這個矛盾必須在 Phase 1 開發排入行事曆前有明確決議**，見第 6 節開放問題新增項目。

**FR-11 資料來源技術方案（2026-09-02 執行計畫書定案）**：第一版**確定採用 Perplexity 的 Agent API（`Create Agent Response` 端點）**，不使用 Router API（`Create Chat Completion` / `Create Response`）——原因：(1) Perplexity 已公告舊版 Sonar／Chat Completions API 將於 2026-09-27 停止支援；(2) Agent API 官方文件明確示範「網路搜尋＋json schema 結構化輸出」搭配使用，符合「依條件即時搜尋→輸出固定格式」的需求，Router API 則需要自行額外串接搜尋工具。呼叫時必須在請求中設定 `response_format` 為 `json_schema`（strict mode）強制輸出格式，**不能只在 prompt 文字裡拜託模型輸出純 JSON**（直接在 perplexity.ai 網站對話框測試會偶爾夾雜額外文字，這是正常現象，因為網站介面沒有這個強制參數）。完整的 System Prompt／User Prompt 樣板、JSON schema 定義、實測問題與對應修正、工程執行步驟，見 [`docs/auth-&-AI-feature-2026-0901/AI選餐廳_Perplexity串接執行計畫書.md`](../../docs/auth-&-AI-feature-2026-0901/AI選餐廳_Perplexity串接執行計畫書.md)（本文件不重複列出，避免兩處內容日後互相漂移）；若 Agent API 測試遇到限制或效能瓶頸，備案是評估 Router API＋自行串接 Google Places API 作為搜尋工具；[docs/auth-&-AI-feature-2026-0901/登入權限與路由控制 & AI 聚餐選餐廳 產品修改規格書 (PRD).md](../../docs/auth-&-AI-feature-2026-0901/登入權限與路由控制%20&%20AI%20聚餐選餐廳%20產品修改規格書%20(PRD).md) 第 4 節提出的方案 A（Google Places API + LLM）則列為效果與成本比較後的備案／並行方案，不是第一版路線。

**FR-12 主揪登入與主揪首頁（2026-09-01 另一份產品修改規格書定案，Phase 1 追加範圍）**

來源：[`docs/auth-&-AI-feature-2026-0901/登入權限與路由控制 & AI 聚餐選餐廳 產品修改規格書 (PRD).md`](../../docs/auth-&-AI-feature-2026-0901/登入權限與路由控制%20&%20AI%20聚餐選餐廳%20產品修改規格書%20(PRD).md) 第 2 節。觸發時機：使用者造訪主站網址（無 `event` 參數）時。

| 子項目 | 規則 |
|---|---|
| 登入技術 | 主揪登入機制限定 **Google SSO 獨佔**，不開放自建帳密、簡訊 OTP、安全提示問題等其他管道——來源文件已逐一評估並排除，理由是開發成本、安全性、第三方簡訊費用等考量 |
| 存取控制 | 未登入時，主站顯示登入畫面，按鈕導向 Google OAuth；OAuth 完成導回站內、前端記下 token 後才視為「已登入」，才能建立活動／瀏覽「我揪的團」 |
| 參與者路由完全不受影響 | 活動專屬連結（`#event=<id>`）**完全免登入**——這條規則優先權高於「主站需要登入」，任何人（含未登入者）都能透過連結投票、查看活動內容，不受這個 FR 影響，見 FR-3／FR-4 |
| 登入後首頁（已定案採**選項 B**） | 頁面分成兩大塊：醒目的「建立活動」大按鈕，另一塊是「我揪的團」過往揪團紀錄列表（不是選項 A 的「單一列表＋頂部新增按鈕」） |
| 「我揪的團」列表規則 | 已取消的活動**一律不顯示給一般使用者**（不論是獨立頁籤或清單裡的狀態標籤都不可見），唯一例外是示範／導覽情境用來展示這個狀態的畫面外觀（見 [04-彈出視窗與全域元件.md「我的聚會／歷史紀錄 Modal」](./頁面規格/04-彈出視窗與全域元件.md#我的聚會歷史紀錄-modal)） |
| Header UI | 登入後右上角顯示主揪頭像；點擊展開下拉選單，提供「登出」，登出後重定向回主站登入頁；Header 為全站共用元件，固定顯示於所有登入後頁面最上方，不隨頁面切換而消失 |
| 登出的即時效力 | 登出後，**即使目前正在瀏覽自己建立的活動頁面**，該頁面也要立即改為呈現「非主揪」視角（隱藏所有主揪限定的操作，包括 FR-5／FR-7／FR-11 的入口），不能因為使用者手上仍握有有效的管理憑證就繼續顯示主揪介面——這裡「目前是否登入」的優先權高於「憑證本身是否有效」 |
| 主揪個人化 | 允許主揪在不同活動使用不同暱稱（「江湖名稱」）保護隱私 |

> ⚠️ **與現有立場的衝突（尚未解決）**：本文件 2.4／8 節「明確排除 OAuth／帳號系統」，且 5.4／5.6 節的主揪身分驗證模型是「姓名＋Email 核對，不使用 token」，兩者都跟 FR-12 這套「強制 Google SSO＋登入態」的設計直接衝突——這是 2026-09-01 另一份產品修改規格書拍板的方向，跟本文件原本「從零開始、核心賣點免登入」的定位是兩條不同的路線。**必須在工程排入行事曆前，由產品與工程一起選邊站，不能兩份文件同時生效**，見第 6 節開放問題新增項目。
>
> **與 prototype 現況的差異**：專案內目前僅有的純前端 prototype 是一個純展示用的靜態頁面（見專案 README.md「專案定位（重要）」），Google 登入僅用畫面模擬（假的跳轉彈窗＋固定延遲，不會真的呼叫 Google API），純粹是為了讓看 Demo 的人理解「這裡未來會是登入情境」——**這不是本 FR 的正式規格，只是現階段 Demo 的簡化表現方式**，正式開發仍須串接真正的 Google OAuth 並補上第 5 節建議技術架構所需的 token 簽發／驗證機制。

**FR-11／FR-12 交會處：AI 選餐廳的存取權限（2026-09-05 定案）**：AI 選餐廳的「產生推薦」入口只對 FR-12 定義的「登入中的主揪」開放；一般參與者、或目前處於登出狀態的主揪，完全看不到這個入口（含整個提示區塊），不是顯示成灰階或禁用按鈕。已經選定的餐廳結果本身則不受此限——所有人（含未登入者）都能看到唯讀結果，只是看不到「試試看」／「重新選擇」按鈕。詳見 4.2 節 FR-11「存取權限」列與 [頁面規格 05-AI選餐廳.md](./頁面規格/05-AI選餐廳.md)。

### 4.3 非功能需求（NFR）

- **資料隱私**：參與者 Email 僅用於通知寄送，需在畫面明確告知用途；不可用於其他行銷或第三方用途
- **主揪身分驗證**：以「主揪姓名（＋活動有登記 Email 時一併核對）」核對取代任何形式的祕密憑證或 token，比對規則見第 5.4 節；伺服器端每次寫入操作（定案／取消／重新開放／編輯）都要重新驗證，不可只靠前端狀態放行。此設計是 Phase 1 刻意接受的風險——未登記 Email 的活動，任何知道主揪姓名（＋活動連結）的人都能取得管理權限，見第 5.6 節與第 6 節開放問題
- **時區**：所有時間一律以台灣時間（Asia/Taipei, UTC+8）認定與顯示，畫面需明確標示「以上時間為台灣時間」
- **防濫用**：投票、留言等公開寫入端點需有基本流量限制，見 4.2 節 FR-9；具體門檻待技術選型後決定
- **規模上限**：單一活動參與人數上限 **50 人**；候選時段上限 **20 個**。達到上限時，前端應阻擋新增／新投票並提示「已達活動人數上限」，後端須二次驗證同一規則
- **可用性**：核心投票流程（開啟連結 → 勾選 → 送出）需在行動網路環境下仍可順暢完成
- **錯誤處理範圍**：Phase 1 的錯誤處理層級以「操作失敗時用 Toast 顯示明確錯誤訊息」為基準；離線偵測、自動重試佇列、資料損毀復原等更進階的容錯機制不在 Phase 1 範圍內
- **Demo／導覽情境**：正式產品需保留簡化過的導覽情境（建議 3–4 組），涵蓋「投票收集中」「已定案」等不同活動階段，並能切換「主揪視角／非主揪視角」，方便展示與新使用者上手，不需要完整複製 prototype 目前的 9 組情境

## 5. 建議技術架構（草案，待工程團隊定案）

> 這一節是**建議方案**，因為目前尚未決定技術棧，以下依據 Phase 1 功能需求推導出一組合理方案，供工程團隊 kickoff 時討論調整。

### 5.1 架構總覽

```
[瀏覽器 SPA / 前端]  →  [後端 API 服務]  →  [關聯式資料庫]
                              ↓                    ↑
                       [通知寄送服務]（Email）   [排程任務：台灣假日資料同步]
```

### 5.2 建議技術棧（待確認）

- **後端**：Node.js，框架可選 Express / Fastify / Hono
- **資料庫**：PostgreSQL（關聯式，適合活動/時段/回覆/留言這種明確關聯結構）＋ ORM（如 Prisma）
- **託管**：可先用單一雲端服務快速上線 Phase 1

### 5.3 資料庫 Schema

- **events**：`id`（見下方「活動 ID」說明）, `title`, `description`, `location_text`, `location_url`, `host_name`（必填）, `host_email`（可為空）, `mode`, `response_deadline`, `status`, `final_slot_id`, `final_note`, `cancelled_at`, `created_at`, `updated_at`——**全表軟刪除**：`status` 變成 `finalized`／`cancelled` 或連結因超過 7 天而失效，都只是狀態欄位變更，記錄本身永不硬刪除，確保未來新建立的活動不會拿到重複的 `id`（2026-09-02 會議定案，見 4.2 節 FR-10 補充）
- **time_slots**：`id`, `event_id`（FK）, `date`, `time`（僅 `time_slots` 模式有值）, `label`
- **participant_responses**：`id`, `event_id`（FK）, `nickname`, `email`, `password_hash`, `comment`, `updated_at`——**唯一性約束**：同一 `event_id` 內 `nickname`（不分大小寫）不可重複，且需與該活動的 `events.host_name` 不衝突（後者建議在應用層驗證，而非資料庫層 constraint，因為要比對的是跨表欄位）
- **response_availability**：`response_id`（FK）, `slot_id`（FK）, `status`（字串欄位，目前 3 個值：available / if_needed / unavailable，需保留擴充彈性）
- **event_comments**：`id`, `event_id`（FK）, `nickname`, `message`, `created_at`, `deleted_at`（軟刪除，供主揪刪除留言使用，而非直接硬刪）
- **taiwan_holidays**：`date`（PK）, `name`, `synced_at`——由排程任務定期同步，見 5.7 節
- **ai_recommendation_usage**（FR-11，2026-09-02 會議追加）：`id`, `host_account_id`（FK，見上方「與現有立場的衝突」說明——此欄位依賴尚未定案的主揪帳號機制）, `event_id`（FK）, `requested_at`——每次「產生推薦」或「重新整理」寫入一筆，用於計算每位主揪當月已使用次數是否達到 20 次上限

### 5.4 API 端點設計

| 方法與路徑 | 說明 |
|---|---|
| `POST /api/events` | 建立活動 |
| `GET /api/events/:id` | 取得活動內容 |
| `PATCH /api/events/:id` | 編輯活動基本資訊（需驗證主揪身分，且僅限「進行中」狀態） |
| `POST /api/events/:id/responses` | 送出或更新參與者回覆（需套用 FR-3 暱稱唯一性規則） |
| `POST /api/events/:id/finalize` | 主揪定案（需驗證主揪身分） |
| `POST /api/events/:id/reopen` | 重新開放投票（需驗證主揪身分，觸發通知） |
| `POST /api/events/:id/cancel` | 取消活動（需驗證主揪身分，觸發通知） |
| `GET /api/events/:id/comments?page=` | 分頁取得留言（每頁 10 筆） |
| `POST /api/events/:id/comments` | 送出留言（套用防濫用頻率限制） |
| `DELETE /api/events/:id/comments/:commentId` | 刪除留言（需驗證主揪身分） |
| `POST /api/events/:id/ai-recommendations` | FR-11：依主揪填寫的（選填）地點與其他偏好，回傳 3–5 間餐廳推薦；每次呼叫計入該主揪當月使用次數，超過 20 次上限需拒絕並回傳明確錯誤 |

**主揪身分驗證方式**：上表標註「需驗證主揪身分」的端點，request body 需附上 `host_name`（若該活動建立時有登記 `host_email`，則同時附上 `host_email`）。後端每次都要重新比對這兩個值是否與該活動 `events` 資料表中登記的完全相符（區分大小寫），驗證通過才能執行操作——不使用 token／session 機制。

### 5.5 通知機制

管道確定為 **Email**（不做 LINE Notify）。觸發通知的事件：主揪定案（FR-6）、主揪取消活動、主揪重新開放投票、（選填）主揪填寫 Email 時的建立成功通知信。**目前不提供退訂機制**——只要參與者留下 Email，上述事件發生時都會收到通知，這是刻意的決定，不是遺漏。發送失敗需記錄，可供之後排查，不可靜默丟失也不可讓整個操作因此失敗回滾。

### 5.6 安全性設計

- 主揪身分驗證：以「主揪姓名＋Email（若有登記）」核對取代任何形式的祕密憑證或 token。**此設計為 Phase 1 刻意接受的風險**：未登記 Email 的活動，任何知道主揪姓名（＋該活動連結）的人都能取得管理權限
- 活動 ID：需為不可預測值（如 UUID 或高熵亂數），避免被枚舉猜出其他人的活動；2026-09-02 會議定案為約 16 字元、不依時間序產生的亂數字串，顯示寬度控制在兩行以內，詳見 4.2 節 FR-10 補充說明
- 輸入驗證：所有寫入端點需伺服器端重新驗證（不可只信任前端驗證）
- 防濫用：投票、留言等公開寫入端點需有基本流量限制

### 5.7 台灣假日資料同步

行事曆／時段選擇畫面上的假日標示，建議改成由後端資料庫維護，而不是寫死在前端程式碼裡。建議做法：排程任務（建議每月執行一次）向 [taiwan-calendar](https://github.com/880831ian/taiwan-calendar) 這類公開資料源抓取最新資料，同步未來一年份的台灣假日資訊寫入 `taiwan_holidays` 資料表，前端透過 API 取得即可，不需要每次發版才能更新年份。

## 6. 開放問題（工程團隊 kickoff 時需一起決定）

1. 主揪姓名「中文 20 字／英文 50 字」在中英混合輸入時的精確計算規則——本文件 4.2 節先訂了「加權字元、上限 40」的預設版本，需要跟產品端再次確認是否採用

4. Google Maps 短連結：正式產品是否要串接真實的解析服務，還是維持只接受完整網址
5. ~~資料保存政策：活動連結失效之後，資料庫記錄要保留多久／是否要提供匯出或刪除機制~~ **2026-09-02 已定案一半**：確定採軟刪除、記錄永不硬刪除（見 4.2 節 FR-10 補充），主要目的是避免新活動 ID 與舊記錄衝突；但「要不要有一天真正清運／封存」「是否提供使用者匯出或要求刪除」仍未決定
6. Should-have 項目（第 2.3 節）是否納入 Phase 1 開發範圍
7. 主揪身分驗證目前刻意採用低安全性的姓名／Email 核對，未來是否需要加強（例如簡單的驗證信流程）
8. 「我的聚會」跨裝置紀錄若未來要做，是否要走輕量 OAuth（例如 Google 帳號）——這會跟「免登入」的核心定位產生張力，需要先在產品定位層級討論清楚，不建議在還沒想清楚前貿然加入
