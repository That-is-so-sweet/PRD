# 揪甘心 — 產品規格文件索引

> 依 `product-manager-skills` 外掛的 `prd-development` workflow skill 產出，並用 `jobs-to-be-done`、`product-strategy-session`、`prioritization-advisor`、`roadmap-planning`、`user-story`（BDD／Gherkin 格式）五個技能補強對應段落。v2 改版方法論調整為「反向從 prototype 的每個功能模組推導問題與隱含假設 → 逐條列成待確認清單 → 跟產品負責人一一定案」，詳見版本紀錄。
>
> **關於 `product-strategy-session`／`roadmap-planning`／`prioritization-advisor` 的重要說明**：這三個技能原本的設計是跨 1-4 週、由 PM＋工程＋設計＋利害關係人共同參與的工作坊流程。這裡沒有真實團隊可以協作，因此對應內容是**協助草擬者依現有素材單獨完成的第一版產出**，所有評分與排序都需要之後找工程／設計一起重新過一次，不能直接當作定案依據。

## 資料夾結構

```
PRD/
├── README.md              — 本檔案，總索引
├── 產品規劃/                — 產品層文件，口語化，方便不同背景的人都能看懂
│   ├── 產品概觀.md          — 一句話說明、問題、使用者、為什麼是現在、怎麼算成功
│   └── 開放問題與規劃.md     — 還沒拍板的問題、優先順序、後續 Phase 規劃、文件強弱點
└── 工程規格/                — 工程團隊直接對照開發與測試用，保留完整技術細節
    ├── 功能需求.md          — 完整 BDD／Gherkin 格式的 User Stories、不做的事、依賴與風險
    ├── 規格書.md            — 技術規格：功能需求細表、資料庫 schema、API 設計、安全性、開放問題
    └── 流程圖.md            — Mermaid 主流程圖與活動狀態轉換圖
```

**分類原則**：「產品規劃」放策略與敘事類內容（問題定義、使用者輪廓、路線圖），寫給不限工程背景的人看；「工程規格」放需要照著實作與測試的內容（驗證規則、資料模型、API、Gherkin Scenario），是給工程團隊的開發依據。

1. **[產品概觀](./產品規劃/產品概觀.md)** — 一句話說清楚、我們要解決的問題、我們在為誰做、為什麼是現在、我們打算怎麼做、怎麼知道有沒有成功
